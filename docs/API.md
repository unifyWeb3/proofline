# API Notes

The repository exposes a Python library, a deterministic fixture CLI, and an
optional same-origin HTTP service for the connected frontend.

## Local library

- `validate_submission(...)` performs fail-closed deterministic preflight.
- `LocalEngine.submit(...)` runs the local fixture path and produces a
  local-provenance receipt for tests.
- `ProoflineDecision.from_dict(...)` parses raw contract decision JSON without
  field renaming.
- `ProoflineReceipt.from_decision(...)` creates local receipts only. Passing
  hosted-looking `FINALIZED` provenance raises `ReceiptError`; hosted receipts
  are constructed internally by `GenLayerLifecycleClient.finalized_receipt(...)`
  after its status, execution, and final-state checks.
- `GenLayerLifecycleClient.inspect(...)` queries a transaction read-only.
- `GenLayerLifecycleClient.finalized_receipt(...)` requires protocol
  `FINALIZED`, SDK execution result `FINISHED_WITH_RETURN`, and `LATEST_FINAL`
  contract readback before constructing `proofline.receipt.v1`. The readback
  decision must match the configured chain and contract, and its canonical
  digest must match the decision effect returned by the producing `submit_job`
  transaction. Finalization comes from
  `consensus_history.current_monitoring.FINALIZED`; acceptance,
  `timestamp_awaiting_finalization`, `last_vote_timestamp`, transaction
  creation, and moving `current_timestamp` are not substitutes. The receipt
  stores integer seconds while the raw authoritative value remains in evidence.
- `LocalAdapter.apply(...)` accepts hosted finalized receipts only when given a
  read-only `lifecycle_client`; it re-observes the transaction and compares the
  latest-final decision before applying the signal. Direct/local receipts
  require explicit `allow_test_receipts=True`.

Validation, evaluator, and lifecycle failures are exceptions rather than
application verdicts. In particular, malformed or contradictory evaluator
output does not become `UNDETERMINED`, stores no decision/replay state, and may
be retried with a valid evaluator result.

## CLI

`python -m proofline.cli fixtures` runs the four deterministic fixtures.
`python -m proofline.cli write-evidence --root fixtures/evidence` writes their
deterministically generated bytes. `python scripts/check_network.py` performs
only read-only `eth_chainId`, `eth_blockNumber`, and best-effort `gen_syncing`
probes.

`scripts/check_network.py` is a read-only chain-identity probe. Hosted writes
are user-authorized in the connected browser through an injected wallet; the
public API does not receive a private key or sign transactions.

## Connected frontend API

`frontend/server.py` is a same-origin API for the static frontend. It uses the
installed RC SDK and does not load a signing account. The prepare endpoints
return unsigned transactions for the browser provider:

- `POST /api/prepare-register`
- `POST /api/prepare-submit`
- `POST /api/build-envelope` derives the artifact, request, response, policy,
  agreement, and evidence digests from canonical user evidence. It returns the
  generated envelope but does not broadcast or persist it.

`POST /api/prepare-register` first checks that `from` matches the owner address
recorded in the finalized deployment evidence; a nonowner is rejected before
fee estimation. This value is only an early guard: a JSON address does not
prove wallet control, and the deployed contract's owner check remains the
final authority. `POST /api/prepare-submit` is not gated by this owner address;
it checks that `from` matches the registered `policy.signer_address`, with the
contract authenticating the actual transaction sender.

These behaviors are live in the existing Vercel Production deployment at
<https://proofline-nu.vercel.app>, configured for Studio Next chain `61997`
and contract `0x30829d13D0d86a9ae83Dc5e832Fb4AADd43Df26b`. A user-performed
injected-wallet browser run registered and submitted fresh job
`browser-1790227078107`. Registration and submission finalized with
`FINISHED_WITH_RETURN / MAJORITY_AGREE`; Production `LATEST_FINAL` returned
`ACCEPT / CRITERION_MET` with matching recomputed digest
`sha256:c1dea2b97956ac766c464e0cb05adbb990c17e79d240ebe6a5e04d183f55a6df`.
Receipt verification passed and LocalAdapter returned `RELEASE_READY`. The
agent independently checked the chain and Production API records but did not

[`evidence/milestone4-browser-verification-20260924.json`](../evidence/milestone4-browser-verification-20260924.json).

The browser broadcasts them with `window.ethereum` and displays the returned
transaction hash. `GET /api/transaction?tx=...` observes registration finality
before submission is enabled. `GET /api/lifecycle?tx=...&job=...` uses the existing
`GenLayerLifecycleClient` and `LocalAdapter`; it does not turn transaction
inclusion into a verdict. `GET /api/readback?job=...&from=...` performs the
authoritative `LATEST_FINAL` contract read. The fresh browser run's transaction,
calldata, digest, finality, receipt, and adapter verification are recorded in
`evidence/milestone4-browser-verification-20260924.json`. No transaction was
broadcast as part of publication synchronization.
